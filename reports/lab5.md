# Lab 5：并发、同步与死锁检测

## 1. 实验目标

本实验在进程地址空间中支持多个内核管理的用户线程，并完成互斥锁、信号量、条件变量和死锁检测。主要目标包括：

1. 理解进程控制块与线程控制块的职责划分；
2. 实现线程创建、退出和等待；
3. 使用阻塞队列实现同步原语；
4. 跟踪线程对资源的请求和占用；
5. 在资源请求真正阻塞前检测不安全状态并返回 `-0xdead`。

## 2. 进程与线程

一个 `ProcessControlBlock` 保存同一进程内所有线程共享的地址空间、文件描述符表、同步对象表和子进程关系。每个 `TaskControlBlock` 则保存独立的内核栈、任务上下文、线程资源、调度状态和退出码。

创建线程时，内核为它分配新的 TID、用户栈和 trap context，但继续引用原进程的页表和文件描述符表。线程退出后保留退出码，主线程通过 `waittid` 回收对应的线程资源。调度器以 TCB 为单位调度，因此同一进程的多个线程可以交替执行。

## 3. 同步原语

自旋互斥锁在锁已被占用时主动让出 CPU，之后重新尝试；阻塞互斥锁则把当前线程加入等待队列并切换任务。解锁时优先唤醒队首线程，没有等待者时才把锁标为未占用。

信号量使用有符号计数器和 FIFO 等待队列。`down` 先减少计数，结果小于零时阻塞当前线程；`up` 增加计数，结果仍不大于零时唤醒一个等待线程。条件变量的 `wait` 操作先释放互斥锁，再进入条件变量等待队列；被 `signal` 唤醒后重新取得互斥锁，从而维持 Mesa 风格的使用语义。

系统调用在取得同步对象的 `Arc` 后释放 PCB 的内部借用，再执行可能发生任务切换的操作，避免跨阻塞点持有内核可变借用。

## 4. 死锁检测状态

互斥锁和信号量分别维护一套资源状态，避免两类资源互相干扰。每套状态包含：

- `Available`：每类资源当前可分配的数量；
- `Allocation[tid][rid]`：线程已经占用的资源数量；
- `Need[tid][rid]`：线程已经提出、但尚未满足的请求数量。

创建互斥锁时登记一个可用实例，创建信号量时登记初始计数。线程请求资源时先增加 `Need`；请求完成后将其从 `Need` 转移到 `Allocation` 并减少 `Available`；释放时执行相反更新。新建或复用 TID 时清空该行的记录。

即使检测开关关闭，内核仍维护资源账目。这样稍后打开检测时不需要猜测此前已经发生的分配状态。开关只决定是否拒绝检测出的不安全请求。

## 5. 检测算法

每次启用检测后的 `mutex_lock` 或 `semaphore_down` 都先暂存本次请求，然后运行安全性检查：

1. 令工作向量 `Work = Available`，所有线程初始为未完成；
2. 查找尚未完成且 `Need[i] <= Work` 的线程；
3. 假设该线程能够运行完毕，将它占用的资源加入 `Work`，并标记为完成；
4. 重复查找，直到没有新的线程可以完成；
5. 若仍有未完成线程，则当前状态不安全。

检测到不安全状态时撤销刚加入的请求并返回 `-0xdead`，不调用底层阻塞操作；否则保留请求，允许线程等待资源。线程被唤醒并真正获得资源后再完成账目迁移。这样既能识别同一线程重复获取同一互斥锁，也能识别多个线程和多个信号量形成的循环等待，同时不会把存在可行完成顺序的请求误判为死锁。

## 6. 累计功能

本分支还保留并适配了前四个实验的功能：跨页用户缓冲区检查、匿名页映射和解除映射、`spawn`、stride 调度优先级、文件元数据以及硬链接。线程模型引入后，地址空间和文件表从单任务结构移动到 PCB，因此相关系统调用都通过当前进程访问共享资源，而优先级仍保存在当前可调度线程中。

使用以下命令运行第八章检查器：

```bash

```

测试覆盖线程参数传递与回收、自旋锁和阻塞锁、信号量、条件变量、管道，以及互斥锁自锁、信号量循环等待和安全资源序列。死锁检测用例中，真正形成不安全状态的请求返回 `-0xdead`，仍存在安全执行顺序的用例全部正常结束。

最终检查结果为 `25/25`，五个累计实验报告均通过存在性检查。

## 8. 实验总结

同步原语不仅要正确维护锁和等待队列，还要保证内核状态更新与阻塞时机一致。死锁检测的关键是把“正在等待”也作为资源图的一部分：请求在阻塞前进入 `Need`，获得资源后才进入 `Allocation`。通过把检测状态放在进程共享结构中，所有线程都能看到统一的资源分配视图，并在进入无法恢复的等待状态前拒绝危险请求。
